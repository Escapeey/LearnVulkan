## 1. 三层设备模型

`VkPhysicalDevice` 和 `VkDevice` 是「发现」和「会话」两件事：

| 维度 | `VkPhysicalDevice`（物理设备） | `VkDevice`（逻辑设备） |
|---|---|---|
| 谁创建 | 驱动/loader 在 `vkEnumeratePhysicalDevices` 时返回给你 | 你调 `vkCreateDevice` 创建 |
| 谁销毁 | **你不能销毁**（根本没有 `vkDestroyPhysicalDevice` 这个函数） | 你调 `vkDestroyDevice` 销毁 |
| 几个 | 系统里有几块 GPU 就能枚举到几个 | 同一块物理设备上**可以有多个** |
| 性质 | 只读的「能力清单」（名称、上限、特性、队列族…） | 带状态的「干活通道」（队列、内存、资源都挂它名下） |

**为什么分两层**:枚举查询是无副作用的「参观橱窗」,真正的资源分配是有状态的「签订合同」。
分层的收益:① 创建逻辑设备前可以先充分查询、比较、选择;② 逻辑设备承载状态与配置,
能隔离应用不同用途(见第 9 题)。

**为什么只有一块 GPU 也分两层**:物理设备解决「发现」(这块卡有什么),逻辑设备解决
「选择后的会话」(我用这块卡、开这些特性、要这些队列)。二者职责不同,即便永远只有一块卡,查询和交互也还是两件事。

## 2. 生命周期

| 对象 | 需要手动销毁? | 为什么 |
|---|---|---|
| `VkInstance` | ✅ `vkDestroyInstance` | 你创建的,根对象,最后销毁 |
| `VkPhysicalDevice` | ❌ | 枚举得来的只读句柄,**没有销毁函数** |
| `VkDevice` | ✅ `vkDestroyDevice` | 你创建的 |
| `VkQueue` | ❌ | 随 `device` **隐式销毁**,没有独立的 `vkDestroyQueue` |
| `VkDebugUtilsMessengerEXT` | ✅ `DestroyDebugUtilsMessengerEXT` | 你创建的,须先于 instance 销毁 |
| `GLFWwindow` | ✅ `glfwDestroyWindow` | 你创建的(GFW 层面,不属于 Vulkan) |

**一句话规律**:Vulkan 里「你显式创建的」才要你显式销毁。`physicalDevice` 是枚举来的,
`queue` 是 `vkCreateDevice` 挂在 device 下的产物,都不需要(也没有)单独的销毁调用。

## 3. `std::optional`

因为 **`0` 是一个合法队列族索引**。图形队列族完全可能是「族 0」,所以 0 不能拿来当「无效」;

- 用 `UINT32_MAX` / `-1` 当魔法值,靠的是「约定」——你得记住"别忘了判这个特殊值",编译器帮不了你;
- `std::optional<uint32_t>` 用**一个额外的 bool 位**显式区分「有值 / 无值」两个状态,
  不占用值域,`has_value()` / `value()` 语义清晰,编译器还能在你误用 `value()` 时兜底。

教程原话「包括 0」说的就是:可选集合里的合法值(0、1、2…)必须和「无效」这个标记**分离**,
魔法值做不到这一点,`std::optional` 做到了。

## 4. 队列族

**1. 能力用什么表示**:`VkQueueFamilyProperties::queueFlags`,一个**位掩码**。
至少四种标志:

- `VK_QUEUE_GRAPHICS_BIT` —— 图形
- `VK_QUEUE_COMPUTE_BIT` —— 计算
- `VK_QUEUE_TRANSFER_BIT` —— 传输(DMA / 拷贝)
- `VK_QUEUE_SPARSE_BINDING_BIT` —— 稀疏绑定

(还有 `VK_QUEUE_PROTECTED_BIT`、`VK_QUEUE_VIDEO_DECODE_BIT` / `ENCODE` 等,本教程用不到。)

**2. 能否同时支持图形+计算+传输**:**可以**。位掩码的每个位独立,判断时分别 `&`:

```cpp
bool canG = family.queueFlags & VK_QUEUE_GRAPHICS_BIT;
bool canC = family.queueFlags & VK_QUEUE_COMPUTE_BIT;
bool canT = family.queueFlags & VK_QUEUE_TRANSFER_BIT;
```

你的 Intel UHD 630 就是活例:族 0 的 flags = `GRAPHICS | COMPUTE | TRANSFER | SPARSE`,一个族全包。

**3. `queueCount` 含义**:是「**这个族里有几个队列**」,不是「系统里有几个队列族」。
一个族可以有多个队列(`queueCount > 1`),创建逻辑设备时你还可以只取其中一部分(通过 `VkDeviceQueueCreateInfo::queueCount`)。

## 5. 队列优先级

**1. 为什么单队列也必须提供**:`pQueuePriorities` 是指针,指向一个「每队列一个 `float`」的**数组**,
数组长度必须等于 `queueCount`。哪怕 `queueCount = 1`,驱动也会读这一个 `float`,所以必须有个真的 `float` 让它读。
优先级(0.0~1.0)是给多个队列争抢时做调度用的;单队列时虽然没竞争,API 仍要求非空。

**2. 生命周期要求**:那个 `float` 必须活到 `vkCreateDevice` **返回之后**。
写成 `pQueuePriorities = &1.0f;` 是**悬垂指针**——`1.0f` 是临时量,取完地址立刻失效,
驱动读到垃圾值 = 未定义行为。这和 D2 的 `debugCreateInfo` 是同一类陷阱:指针存的是「地址不是拷贝」。
正确写法是把 `float queuePriority = 1.0f;` 定义成命名变量,作用域覆盖 `vkCreateDevice` 调用。

## 6. 前瞻题:D5 的 presentFamily

**1. 你的机器(单 Intel 集显)**:`graphicsFamily == presentFamily == 0` —— **同一个族**。
你的机器只有族 0 一个队列族,而它既支持图形又能呈现,所以两者必然相同。
(得益于 `your-gpu.md` 第 4 节:D5 的 `imageSharingMode` 会走 `EXCLUSIVE`。)

**2. 双显卡笔记本(Intel 集显 + NVIDIA 独显)**:
- **NVIDIA 独显**负责渲染 → `graphicsFamily` 落在 NVIDIA(族 N)
- **Intel 集显**负责连屏幕(尤其节能模式下)→ `presentFamily` 落在 Intel(族 I)
- 两者**不同**,因为「能画」和「能把它送到显示器」是两件事,只有**接到屏幕的那块卡**才「能呈现」。

**3. 怎么处理才不重复请求**:
用 `std::set<uint32_t> uniqueQueueFamilies` 去重——把 `graphicsFamily` 和 `presentFamily` **都**塞进集合,
`std::set` 天然去重,再对集合里每个族分别构造一个 `VkDeviceQueueCreateInfo`。
两者相同时 set 里只有一个元素(创建一次),不同时有两个(创建两次)。D5 就会这样做。

## 7. 实例扩展 vs 设备扩展

**1. 区别**:作用范围不同。

| | 实例扩展 | 设备扩展 |
|---|---|---|
| 挂在哪 | `VkInstance` 层面 | 某一块物理/逻辑设备 |
| 是「谁的」能力 | **整个 Vulkan 会话**的能力 | **某一块具体显卡**的能力 |
| 例子 | `VK_EXT_debug_utils`、`VK_KHR_surface` | `VK_KHR_swapchain` |

**2. `VK_KHR_swapchain` 是设备扩展**:因为「能不能把图像呈现到显示器」是**某一块具体显卡**的能力。
有些设备是纯计算卡 / 服务器卡,根本没有显示输出——它照样能做 Vulkan 计算,但不能呈现。
既然能力随设备而异,它就属于设备扩展,而不是「会话初始化一次」的实例扩展。

## 8. 设备的验证层字段

**1. 现代实现会忽略它们**。Device Layer 从 Vulkan 1.0 起就**从未真正生效过**,现代规范直接要求
`VkDeviceCreateInfo::enabledLayerCount` 必须为 0。所以设这些字段会触发验证层警告——
**你现在跑 D3 应该已经看到这条了**:

```
validation layer: vkCreateDevice(): pCreateInfo->enabledLayerCount is 1 (not zero).
Device Layers have never worked since Vulkan 1.0 ... enabledLayerCount must be 0
```

**2. 教程为什么还设**:历史遗留。早期 API 设计预留了「设备层」(device layers),后来废弃了,
但教程代码没及时更新。照设无害(被忽略,不影响功能),但**现代正确做法是干脆不设**,让
`{}-初始化`默认的 0 起作用即可。⚠️ D4 改 `createLogicalDevice` 时顺手把它删掉(见 D4 骨架里的 TODO)。

## 9. 多个逻辑设备

从同一块物理设备创建多个逻辑设备,有意义在**隔离不同用途的状态**:

- **一个应用同时干多种活**:主渲染 + 物理模拟的 GPU 计算 + 独立的编辑器预览视口,
  分别为它们建各自配置的逻辑设备(不同队列、不同扩展、不同特性开关),互不干扰;
- **库 / 中间件需要隔离**:一个第三方渲染库想拥有自己的 Vulkan 状态,不污染主应用的 device;
- **按需开特性**:比如一个 device 开了 `geometryShader` 特性,另一个只做纯计算,省去特性开关的全局影响。

代价:资源(内存、缓冲、描述符集…)都在各自 device 内,**不共享**,跨 device 要显式传输。
所以是「隔离换独立」,不是免费的。

## 10. 会成长的函数

`isDeviceSuitable()` 现在只是 `indices.isComplete()`,后续至少会新增:

| 新增检查 | 对应章节 |
|---|---|
| 设备扩展支持(`VK_KHR_swapchain` → `checkDeviceExtensionSupport`) | D4 |
| 交换链能力充分(`formats` / `presentModes` 非空 → `swapChainAdequate`) | D4 |
| 呈现队列族 `presentFamily`(`QueueFamilyIndices` 长大) | D5 |
| 各向异性过滤特性(`deviceFeatures.samplerAnisotropy`) | D17 |
| 深度格式支持(`D32_SFLOAT` 等 → `findSupportedFormat`) | D19 |

规律:每一项都是「这块卡**必须具备的能力**」的硬性检查,`isDeviceSuitable` 是它们的汇总门禁。

**追问**:你的 Intel UHD 630 **只有 1 个队列族**(族 0)。
- 图形 ✅ 和计算 ✅ 在**同一个族**(族 0);

## 12. 延伸思考

**对游戏引擎**:GPU 选择从「驱动面板这类非 API 手段」变成了**可编程的 API**。Optimus 笔记本上
「游戏默认跑在集显上」的经典坑,引擎现在能:枚举所有 GPU → 评分(独显 +1000)→ 显式指定 NVIDIA 独显,
还能做多 GPU 负载均衡、按用户设置/外接屏情况选卡。这是一等公民能力,不再靠猜。

**对你的代码**:`pickPhysicalDevice` 写错,在自己机器(只有一块 GPU)上完全正常,在别人
(双 GPU)机器上可能选中错误的卡 → 性能腰斩。防法:

1. **评分 + 硬性要求**:独显加分、`geometryShader` 这类硬要求直接返回 0 淘汰(你现在这套已经做了);
2. **打印选中设备名**:一眼能验证「选的是不是我想的那块」;
3. **允许覆盖**:命令行参数 / 配置指定首选设备,而不是硬编码「挑分数最高的」;
4. **多 GPU 机器实测**:这是唯一能真正暴露这类 bug 的办法(和验证层一样——没环境就测不出来)。
